# Split tunneling по списку доменов и подсетей (macOS)

Дата: 2026-08-16
База: `netbirdio/netbird` v0.77.0
Ветка: `split-tunnel`

## Проблема

Management-сервер отдаёт клиенту единственный тип маршрута — `0.0.0.0/0`: одну
HA-группу `Auto (Load Balancer)` и пять отдельных exit-нод. Внутренних подсетей
нет. Клиент разворачивает `0.0.0.0/0` в пару `0.0.0.0/1` + `128.0.0.0/1` и
уводит в туннель весь трафик машины.

Встроенный селектор (`netbird networks select/deselect`) задачу не решает:
выбирать не из чего, все доступные маршруты — это `0.0.0.0/0`. Настройки на
сервере недоступны, менять их некому.

Нужно: через VPN ходят только рабочие сервисы (`gitlab.example.com` и
подобные), весь остальной трафик идёт напрямую. Требование пользователя —
решение должно переживать переподключения и HA-переключения само, без внешних
скриптов, и не пропускать нецелевой трафик в туннель ни на секунду.

## Что установлено экспериментально

Проверено на живой системе 2026-08-16.

Рабочие сервисы доступны по публичным адресам, отфильтрованным по IP на стороне
провайдера. Оба проверенных сервиса ведут себя одинаково — `HTTP 403` без VPN и
`HTTP 302` через VPN:

| сервис | инфраструктура | адреса | TTL |
|---|---|---|---|
| `gitlab.example.com` | AWS ELB (`eu-west-2`) | `192.0.2.10`, `192.0.2.11`, `192.0.2.12` | 60 c |
| `jira.example.com` | AWS CloudFront | `192.0.2.20` | 60 c |

DNS перехватывать не нужно: NetBird-резолвер (`10.0.0.253`) возвращает для
этих доменов ровно те же публичные адреса, что и `1.1.1.1`. Задача чисто
маршрутная.

Ключевая проверка — split tunneling достигается управлением одними лишь
системными маршрутами, без правок WireGuard, сервера и ACL:

| состояние | exit IP общего трафика | gitlab |
|---|---|---|
| полный туннель (как есть) | `198.51.100.23` (exit-нода) | 302 |
| сняты `0/1` и `128.0/1` | `203.0.113.10` (домашний) | 403 |
| + `route add -host <3 адреса> -interface utun100` | `203.0.113.10` (домашний) | **302** |

У exit-пира `AllowedIPs = 0.0.0.0/0`, поэтому туннель принимает любой адрес —
вопрос только в том, какие префиксы в него направлены. Ручные маршруты пережили
60 секунд HA-переключений: route manager их не реконсилит, дефолтные маршруты
переустанавливаются только при переподключении.

## Цель и границы

Цель: клиент ставит маршруты в туннель **только** для заданного списка доменов и
подсетей, никогда не устанавливая маршрут по умолчанию.

Не входит в задачу:

- маршрутизация по приложениям (macOS этого через таблицу маршрутов не умеет);
- изменения на management-сервере;
- поддержка платформ кроме macOS — код пишется платформенно-нейтральным, но
  проверяется только на darwin;
- сохранение совместимости с апстримом ради будущего PR.

## Архитектура

### Точка врезки

Маршруты от сервера приходят в единственный метод —
`DefaultManager.UpdateRoutes` (`client/internal/routemanager/manager.go:412`),
параметр `clientRoutes route.HAMap`. Врезка идёт туда — строго **после**
`m.routeSelector.FilterSelectedExitNodes(clientRoutes)` и до
`updateSystemRoutes` / `updateClientNetworks`.

Порядок принципиален. `isExitNode` в
`client/internal/routeselector/routeselector.go:342` опознаёт exit-ноду по
`Network == 0.0.0.0/0`; переписанный маршрут этой проверки уже не проходит.
Врезка до фильтрации означала бы, что применяются все шесть присланных
default-маршрутов (`Auto (Load Balancer)` плюс пять exit-нод) — шесть групп
маршрутов на одни и те же домены через разных пиров. После фильтрации остаётся
только выбранная группа, её и переписываем.

Побочная выгода: в `m.clientRoutes` сохраняются исходные маршруты, поэтому
`netbird networks ls` показывает привычный список, а выбор exit-ноды в UI и CLI
продолжает работать без изменений.

Отвергнутая альтернатива — патчить `genericAddVPNRoute`
(`client/internal/routemanager/systemops/systemops_generic.go:212`), где
`0.0.0.0/0` разворачивается в две `/1`. Там пришлось бы самостоятельно писать
резолв доменов, таймер обновления, refcounting и откат при отключении, то есть
дублировать уже существующую подсистему.

### Механизм: подмена маршрута, а не подмена маршрутизации

В `route.Route` (`route/route.go:94`) поля `Network` и `Domains` взаимоисключающие,
а `IsDynamic()` — это `NetworkType == DomainNetwork` (`route/route.go:179`).
Значит маршрут по умолчанию можно переписать в domain-маршрут:

```
было:  {Network: 0.0.0.0/0, NetworkType: IPv4Network,   Peer: peer-a, NetID: "Auto (Load Balancer)"}
стало: {Domains: [gitlab.example.com], NetworkType: DomainNetwork, Peer: peer-a, NetID: "Auto (Load Balancer)"}
```

Для остального клиента результат неотличим от легального domain-маршрута,
какие сервер и так умеет присылать. Благодаря этому бесплатно переиспользуются:

- периодический ре-резолв доменов (`client/internal/routemanager/dynamic/route.go`,
  интервал уже настраивается флагом `--dns-router-interval`, по умолчанию 1 минута) —
  решает проблему плавающих адресов ELB;
- HA и выбор exit-ноды: поле `Peer` не меняется, переключение между нодами работает;
- refcounting маршрутов и AllowedIPs, включая корректный откат при `netbird down`;
- отображение резолвленных доменов в `netbird status` и в UI.

Статические подсети добавляются вторым случаем: синтетический `route.Route` с
`Network: <cidr>`, `NetworkType: IPv4Network` и тем же `Peer`.

### Плавающие адреса за CDN

Оба сервиса отдают записи с TTL 60 секунд, а Jira живёт на CloudFront, где адрес
может смениться в любой момент. Опасность не в самой смене, а в рассинхроне:
браузер резолвит домен сам и может получить адрес, которого ещё нет в таблице
маршрутов, — тогда запрос уйдёт мимо туннеля и получит 403.

Решение — выставлять на переписанном маршруте `KeepRoute: true`. В
`dynamic/route.go:311` удаление устаревших префиксов начинается с проверки этого
флага и при нём не выполняется вовсе: адреса только накапливаются. Сменился
адрес CDN — новый маршрут добавился, старый остался, доступ не прервался. За
сессию накапливаются единицы-десятки маршрутов, при переподключении список
обнуляется.

Механизм `client/internal/routemanager/dnsinterceptor` для этой задачи не
подходит, хотя внешне решает ту же проблему: он рассчитан на домены, которые
обслуживает пир-роутер со своим DNS-форвардером, и работает через fake IP с
DNAT. Наши домены публичные, такого пира в сети нет.

Маршрут `0.0.0.0/0` в системе не появляется, `genericAddVPNRoute` с дефолтным
префиксом не вызывается вовсе. Окна утечки нет по построению — не потому что оно
быстро закрывается, а потому что перехвата не происходит.

### Новый код

Файл `client/internal/routemanager/splittunnel.go`, чистая функция плюс
разбор конфигурации:

```go
// Spec — разобранный список из конфигурации.
type Spec struct {
    Domains  domain.List
    Prefixes []netip.Prefix
}

// ParseSpec разбирает список из конфигурации. Строка, разбирающаяся как
// netip.Prefix, считается подсетью, остальное — доменом.
func ParseSpec(entries []string) (Spec, error)

// Transform переписывает маршруты по умолчанию в domain-маршруты и добавляет
// маршруты для статических подсетей. Маршруты, не являющиеся дефолтными,
// проходят насквозь без изменений.
func Transform(routes route.HAMap, spec Spec) route.HAMap
```

Поле `Domains` в `route.Route` имеет тип `domain.List`, то есть один маршрут
несёт сразу несколько доменов. Поэтому **все** домены из списка кладутся в один
переписанный маршрут, а не порождают по маршруту на домен. Каждая статическая
подсеть, наоборот, требует отдельного `route.Route` (поле `Network` — одиночный
префикс); такие маршруты добавляются в ту же HA-группу с тем же `Peer`, получая
собственные `ID` и `NetID` с суффиксом, чтобы не конфликтовать с исходным.

## Конфигурация и CLI

Один флаг, значения через запятую:

```
netbird up --split-tunnel gitlab.example.com,jira.example.com,10.50.0.0/16
netbird up --split-tunnel ""      # выключить, вернуться к полному туннелю
```

Плуминг по образцу существующего `DNSLabels` (slice-поле с очисткой пустой
строкой), четыре точки:

1. `client/cmd/system.go` — константа флага и переменная;
2. `client/cmd/up.go` — регистрация через `StringSliceVar`, передача в
   `ConfigInput` при `cmd.Flag(...).Changed`;
3. `client/internal/profilemanager/config.go` — `ConfigInput.SplitTunnel *[]string`
   (строка ~92), `Config.SplitTunnel []string` (строка ~134), применение в
   `apply` (строка ~526);
4. `client/internal/routemanager/manager.go` — поле `ManagerConfig.SplitTunnel`,
   сохранение в `DefaultManager` (строка ~140), использование в `UpdateRoutes`.

Список сохраняется в профиль, поэтому обычный `netbird up` и любые
переподключения подхватывают его сами. Это закрывает требование о том, что
настройка не должна теряться, штатным механизмом конфигурации.

## Краевые случаи

- **Сервер не прислал `0.0.0.0/0`.** Переписывать нечего, привязать
  domain-маршрут не к чему (нужен `Peer`). Пишем warning в лог, подключение не
  ломаем, маршруты пропускаем без изменений.
- **`0.0.0.0/0` приходит HA-группой.** Переписываем все маршруты группы,
  сохраняя `Peer` у каждого, чтобы HA-переключение продолжало работать.
- **Домены ещё не зарезолвлены** в первые секунды после подключения. Рабочий
  сервис в этот момент отвечает 403, потому что трафик идёт мимо VPN. Отдельного
  механизма не строим: приватность не страдает, лечится повтором запроса.
- **IPv6.** Сейчас клиент ставит v6-blackhole в довесок к `0.0.0.0/0`
  (`systemops_generic.go:232`). При split tunneling этого не происходит, IPv6
  идёт напрямую — поведение соответствует цели.
- **Пустой список при включённом флаге** эквивалентен выключенному split
  tunneling: маршруты проходят насквозь, туннель работает как раньше.
- **Домен не резолвится.** Существующий resolver уже уменьшает интервал до 5
  секунд при ошибке (`dynamic/route.go`, `failureInterval`), отдельной обработки
  не требуется.

## Тестирование

Порядок TDD: сначала тест, потом реализация.

**Юнит-тесты** на `Transform` — чистая функция, работает без сети и без root:

- маршрут `0.0.0.0/0` превращается в domain-маршрут с сохранением `Peer`, `NetID`, `ID`;
- на переписанном маршруте выставлен `KeepRoute: true`;
- HA-группа из нескольких пиров переписывается целиком, `Peer` у каждого сохраняется;
- недефолтные маршруты проходят без изменений;
- строка-подсеть даёт маршрут с `Network`, строка-домен — с `Domains`;
- пустой список оставляет маршруты нетронутыми;
- отсутствие дефолтного маршрута не приводит к ошибке.

**Натурная проверка** на живой системе, без единой ручной команды `route`:

1. `netbird up --split-tunnel gitlab.example.com,jira.example.com`;
2. общий трафик выходит с домашнего адреса (`curl https://1.1.1.1/cdn-cgi/trace`);
3. `gitlab.example.com` и `jira.example.com` отвечают 302;
4. в таблице маршрутов нет `0/1` и `128.0/1`, но есть точечные маршруты на адреса ELB;
5. после `netbird down && netbird up` без флагов поведение сохраняется;
6. переключение exit-ноды не ломает доступ к сервису.

## Сборка и установка

Требуется Go 1.25.5 (на машине не установлен, ставится через `brew install go`).

Собирается только демон `netbird`. GUI `netbird-ui` не трогаем: он общается с
демоном через `unix:///var/run/netbird.sock` и о подмене не знает.

Установка: сохранить оригинал как
`/Applications/NetBird.app/Contents/MacOS/netbird.orig`, положить свой бинарь на
его место, подписать ad-hoc (`codesign -f -s -`), перезапустить сервис через
launchd (`/Library/LaunchDaemons/netbird.plist`).

## Риски

- **Автообновление NetBird затрёт форк.** Придётся пересобирать после обновлений.
  Принято сознательно при выборе подхода.
- **Ad-hoc подпись ломает подпись бандла.** Для локально запускаемого
  launchd-демона это приемлемо; при проблемах запасной вариант — ставить свой
  бинарь отдельным путём и править plist.
- **Расхождение с апстримом.** Патч намеренно локализован в одном новом файле и
  четырёх точках плуминга, чтобы упрощать перенос на новые версии.

## Известные ограничения

**Android не поддержан.** `CurrentRouteRange` (`client/internal/routemanager/manager.go:497`)
отдаёт список маршрутов для TUN-интерфейса, минуя трансформацию: он вызывает
`FilterSelectedExitNodes` напрямую. Оба его потребителя платформенные —
`client/internal/engine.go:2136` внутри `switch runtime.GOOS { case "android" }`
и `client/internal/engine_tunsettings.go` → `client/android/client.go:281`. На
darwin путь недостижим, поэтому в рамках задачи он не менялся, но при сборке
форка под Android split tunneling там не сработает: в TUN уйдёт исходный
`0.0.0.0/0`, то есть весь трафик. Прежде чем собирать под Android, нужно
провести и этот вызов через `DefaultManager.selectedRoutes`.

**DNS-метаданные продолжают идти на корпоративный резолвер.** Сервер раздаёт
nameserver-группу, обслуживающую корневую зону
(`client/internal/dns/server.go:886`), поэтому при включённом split tunneling
TCP-соединения идут напрямую, а DNS-запросы обо **всех** доменах — по-прежнему
через туннель на `10.0.0.253`. Цель «весь остальной трафик идёт напрямую»
для DNS не достигается. Оба рабочих домена — публичные и резолвятся публичными
резолверами идентично (проверено), поэтому рабочее обходное решение —
`netbird up --disable-dns`; ценой станет потеря резолва внутренних имён
`*.internal.example.com`.

**AAAA рабочих доменов уходят в туннель.** Резолвер динамических маршрутов
добавляет и IPv6-префиксы, а v6-адреса у интерфейса туннеля нет, и v6-blackhole
при split tunneling не ставится (он вешается только вместе с `0.0.0.0/0`,
`systemops_generic.go:227-235`). `jira.example.com` за CloudFront
двухстековый, поэтому поведение проверяется отдельным шагом натурного сценария
(Task 6, Step 8b).
